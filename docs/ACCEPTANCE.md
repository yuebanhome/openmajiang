本批修复保持 8 桌并发、25 ms 数据库发现周期、8 连接默认池、生产时钟、全部人数与 100 ms 门槛不变：

- 调度器保留有序待办队列，worker 完成立即补位；满载时仍刷新过期优先级，移除已经被外部操作推进的条目。每桌仍在原行锁与租约检查下重新判断状态。新增单次发现 50 桌、满载刷新/去重与取消退出回归。
- MCR 增加兼容旧插件的可选批量投影，对一个不可变快照完整解析/校验一次后独立序列化公共与各私人视图。保留公开弃牌白名单、各参与者分行落库及原事务；插件未实现可选接口时仍逐个投影。
- 公共缓存预编码不含数据库序号/决策的 WebSocket 正文；每条连接独立追加 stream/view 序号，无需重新解码整个观战局面。保持强制 resume、换手换 stream、同序号元数据变化和缓存失效语义。

定向调度/公共 WebSocket race 回归，以及批量投影跨阶段等价、隐藏牌隔离、无效快照拒绝、旧插件 fallback 和可执行产物包装转发测试通过。五视图配对微基准中位耗时从 634.069 µs 降到 158.555 µs，分配从 283,038 B / 1,178 次降到 71,277 B / 269 次；每个快照仍经过完整库存校验。观战小帧配对微基准（本地 Go 1.27.1、AMD EPYC 9V74）旧路径约 9.3–9.6 µs / 4,249 B / 77 次分配，新路径约 0.27–0.29 µs / 400 B / 4 次分配；这只代表相同测试帧的组装，不代表端到端容量已通过。本机没有可运行的 PostgreSQL，数据库用例明确跳过，仍须提交后的真实 CI 与完整一小时报告验证。

## 第七轮结果与锁等待修复

[第七次 CI](https://github.com/yuebanhome/openmajiang/actions/runs/36280326051) 的 PR 头为 `ac1bcea815dc0e69f55b1340f4c19a8d7d454015`。双架构完整 verify 通过；本批提交时 WSS 长测仍运行，不能据旧轮次结果宣称该提交全部通过。

[第七轮容量原始报告](evidence/ci-36280326051-capacity.json) 完整测量 3,600.001 秒，仍失败：ACK p95 **184.351 ms**、裁决 p99 **408.430 ms**；最低 80 玩家 / 1,110 观众、3,590 次人数采样零缺口、协议错误 0、10/10 慢消费者释放、2,551 手 / 134 场。含客户端的进程 CPU 从第六轮 6,282.947 秒降到 2,706.147 秒，但累计空池等待从 12,159.282 秒增至 66,521.928 秒；获取次数反而下降约 4%，说明不能仅继续按 CPU 热点解释尾延迟。

两轮机器并不相同：第六轮 AMD EPYC 7763 / northcentralus，第七轮 Intel Xeon 6973P-C / centralus，均为 4 核、相同 Go、runner 镜像及 PostgreSQL 17.11 容器摘要。普通 WAL checkpoint 的 sync 中位数从 0.026 秒增至 0.380 秒；启动、负载开始前的 checkpoint 同步也更慢。此证据支持检查存储等待，但 checkpoint 时长并不是事务提交时延，不能据此断言全部回退来自硬件。

代码中确认并修复以下阻塞路径：

- 心跳单次更新多桌租约，会等待任意忙桌并持有先前取得的其他桌行锁。现在通过 `FOR UPDATE SKIP LOCKED` 只续租可立即锁定的合法记录，保留 1 秒重试、5 秒续租、3 秒触发和所有归属/未过期条件。
- 定时工作遇到玩家提交持有的行锁时立即释放连接并留待下一轮发现；玩家提交及管理操作继续正常串行持锁，不改变 ACK 提交与幂等边界。
- 非法选项拒绝时，先回滚仅做读取的验证事务，再独立记录统计，避免持有池连接又等待同一池的第二条连接；新增单连接池拒绝与统计去重回归。
- 数据库发现改为最多一个异步查询；查询等待连接时，调度循环仍接收完成事件并补位。过滤查询期间已派发记录，避免陈旧结果再次排队。仍为 8 个定时 worker、25 ms 发现周期、默认 8 条应用连接。

新增 PostgreSQL 锁回归保留忙桌锁，验证空闲桌续租不中断、过期/外部归属/非活动/新鲜租约不被修改，以及忙桌定时重试恰好裁决一次；真实执行交 CI。容量报告新增独立诊断连接的数据库等待采样，不占应用池连接，统计采样覆盖与失败。采样为 100 ms 周期的会话观测计数，不是每个事务的精确计时；诊断连接的数据库及进程开销包含在实测负载中。

CI 先在同一 runner 上用同一完整负载、时钟及延迟阈值运行 6 分钟诊断并上传报告，尽早暴露失败；诊断 `purpose=diagnostic`、`passed=false`，不能计为容量验收。只有随后原样完成一小时测试且 `passed=true`、实际时间至少 3,600 秒，容量 job 才能通过。诊断失败时保留红色检查，绝不缩短正式门槛。

本批本地全仓 `go vet` / Go race 通过；最后的非法选项分支另行通过定向 vet / race。所有新增真实 PostgreSQL 回归在本机明确跳过，须由新提交的 CI 验证。

## 可复现命令

环境：Go 1.27.1，CGO/C++，Node 24，PostgreSQL 17。CI 分别使用原生 `ubuntu-24.04` / `ubuntu-24.04-arm`。环境配置和容器启动见 [部署文档](deployment.md)。

```sh
cd web
npm ci
npm run typecheck
npm test
npm run build
cd ..
go vet ./...
go test -race -count=1 ./...
MCR_SOAK_MATCHES=625 go test ./rules/mcr -run '^TestSoak$' -count=1 -timeout=10m
go run ./cmd/bot-runner -local -hands 16 -strategy basic_heuristic
```

没有数据库变量的本机命令不代替 CI 数据库结果。API 生成和校验见 [api/README.md](../api/README.md)，外部 WSS 及固定依赖见 [sdk/integration/README.md](../sdk/integration/README.md)。一小时容量必须显式设置 `OMJ_CAPACITY_SECONDS=3600`、`OMJ_CAPACITY_REPORT` 和真实数据库地址；短运行不能标记验收通过。

## 规则解释与发布边界

规则来源锁定 WMO 2014 第二版，线上补充锁定 `om-mcr-1`；来源、许可证、上游适配及“多杠时加计最高暗杠类别”的明确解释见 [scoring/NOTICE.md](../rules/mcr/scoring/NOTICE.md)。规则牌例与程序审查不等于外部裁判认证。复杂拆分穷举范围、测量机器及原始数据见 [PERFORMANCE.md](../rules/mcr/scoring/PERFORMANCE.md)；三家同时可和的 1,000 次裁决加五个投影实测 p95 1.703 ms、最大 4.636 ms，不含数据库/网络。后续行为变更必须升版，不能静默改写历史。

CI WebKit / Chromium 和移动视口验证仅代表对应浏览器引擎的自动化结果，不等于真实 iPhone / Android 设备实测。容量报告会记录机器、同机客户端负载、局数、连接数及延迟，不把局域测试延迟等同于公网体验。

PR 尚未合并，不存在已部署服务器或已验证 Docker Hub 发布的声明。所有未通过或尚未执行的门槛必须继续保留，不能只因实现完成就勾选。
