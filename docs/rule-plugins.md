# 规则插件开发契约

插件是经过代码审查、编译进服务的 Go 包。首版不加载任意 `.so`、不调用 `plugin.Open`，不接受用户上传可执行裁判代码。新增规则需实现 `pkg/rulesdk.Rule`，在 `rules/registry` 显式注册，并提供兼容的前端 renderer；账号、会话、房间和 Bot 连接复用平台。

## 职责

| 接口 | 插件负责 | 平台负责 |
| --- | --- | --- |
| `Manifest` | 规则身份、版本、支持人数/赛程/线上口径、状态格式、能力、实现哈希 | 展示目录、冻结版本、恢复兼容性检查 |
| `ValidateConfig` | 验证插件自身配置 | 身份、模式、邀请、准备、并发席位资格 |
| `Init` | 用宿主秘密熵产生确定性初始状态 | CSPRNG 熵、数据库事务、固定参赛身份 |
| `Inspect` | 当前阶段、席位映射、本人的合法选项、结束标志、比分 | 时钟、控制权、消息路由 |
| `Apply` | 验证动作、响应优先级、计分、确定性状态迁移 | 幂等、串行事务、截止时间、持久化、ACK |
| `Project` | 分别构造本人或弃牌观战 DTO | 再次验证观战白名单、权限、独立流与回放 |

`Snapshot` 是平台不解释的 JSON。插件不可使用网络、数据库、当前时间或全局随机数；相同初态和 `Input` 必须产生相同新状态。非法输入不能部分修改旧状态。

`Participant.ID` 在整场稳定。座位、庄家与门风可以每手变化；累计分始终绑定参赛身份。`Flow.Assignments` 和 `Flow.Decisions` 不限四人；赢家数量、支付方式、连庄和赛程终止由插件决定，平台不能自行套国标规则。

## 决策与窗口

`WindowKind` 使用 `self`、`reaction`、`intermission`、`ended`。每次合法选项或阶段变化必须更新 `WindowID`，并生成该身份独有的 `Decision.ID`。`option_id` 由裁判产生，客户端只能从收到的合法选项中选择。

- `action` 处理单个当前决策；插件必须校验参赛身份与选项。
- `resolve` 接收已持久化的响应 `Choices`；插件统一裁决，不能信任客户端声明优先级。
- `timeout` 使用规则明确允许的默认行为；不可进行非法动作。
- `next_hand` 只能在手间调用，插件负责是否连庄、换位或结束。

平台在同一事务锁下处理动作和计时器。响应窗口即使提前收齐也等待固定截止，避免从等待时长推断其他人的合法选项。国标的普通补花会生成新决策，但保留当前行动的原始截止时间。

## 视角

`ParticipantPrivate` 只投影请求参赛者当时可见的信息，不能返回其他人的隐藏手牌、未公开意向、完整牌墙或随机种子。公开副露和补花仅指向同场参赛者公开。

`SpectatorDiscardOnly` 必须提供 `spectator_discard_only@1`。唯一允许的牌面数组是已经发生的 `discards`，每项包括 `discard_id`、`from_seat`、`kind`、`claimed`。观战数据禁止出现物理 `tile_id`，也不包括副露牌面、补花牌面、获胜成牌、暗杠牌面和逐番拆分。历史回放与结束状态使用同一限制。

平台对未知观战字段直接拒绝；不要为扩展规则增加任意 `metadata` 绕过白名单。新增无牌面字段需要明确契约与测试。新的牌种也需要配套的可见弃牌格式和 renderer 版本。

## 版本冻结

国标标识为 `openmajiang.mcr@1.0.0`，来源 `wmo-mcr-2014-2nd`，线上口径 `om-mcr-1`。`standard_16`、`practice_1` 和 `practice_4` 是独立赛程，不伪装成规则版本。

影响合法动作、支付或可见性的变更必须升规则版本。`source_hash` 标识国标 Go/C++ 与实际 SDK 契约源码，排除测试、文档和测量结果；它用于说明规则的源码身份。

生产注册表在启动时计算当前 Go/CGO 可执行文件的 SHA256（Linux 读取 `/proc/self/exe`），把它作为 `artifact_hash` 绑定到所有实际加载的插件，并记录 Go 版本、操作系统和架构。规则模块自身不读取文件。平台目录、开局冻结和恢复都使用这个已绑定的 Manifest，而不是把源码哈希冒充二进制产物哈希。镜像 digest 另外固定系统库与容器环境。

因此即使只修改内嵌前端、构建参数、编译器或目标架构，也会保守拒绝用新二进制恢复旧的进行中比赛。首版升级必须先维护、排空旧比赛，再更换镜像；不能宣称跨构建或跨架构无缝接管。保留旧 digest 才能按原产物恢复。历史已过滤回放与结算摘要按保留期读取，不用新裁判重算旧分数。

## 最低测试要求

1. 配置与状态边界校验、确定性、非法输入原子性、所有合法动作及冲突优先级。
2. 牌张/资源守恒、每次结算零和或插件规定的支付不变量、真实终止条件。
3. 正常、结束和回放阶段的本人及观战投影；不能只测试浏览器隐藏元素。
4. 跨手席位映射、幂等重试、过期授权、恢复与版本不兼容。
5. 规则来源及线上补充的明确牌例；第三方算分库默认行为不等于选定规则文本。

`internal/testplugins/threeplayer` 是不注册到生产的契约夹具：三名玩家、同手两名赢家、庄家重复、两手结束。它用于验证宿主没有把四人、单胡、国标轮庄或 16 手写死，不能当作另一套可玩的正式麻将规则。
